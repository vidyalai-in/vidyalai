## Q6. Reduce LLM cost by 70% without hurting quality
### Short answer
A 70% cut almost never comes from one trick. It comes from stacking three or four multiplicative levers on a cost model you have actually measured: caching the prompt prefix, routing easy traffic to a smaller model, sending non-interactive work through batch, and trimming wasted tokens. Combined, these remove 70-85% of spend (for example 0.5 x 0.6 x 0.8 ≈ 0.24 of the original bill). Before touching anything I build a frozen eval set and a quality guardrail metric, so "without hurting quality" is something we test, not something we hope for. Then I roll out one lever at a time behind a flag and measure against that guardrail.
### Detailed answer
#### Clarify first
  - **What does the spend actually consist of?** Break it down by endpoint and feature, input vs. output tokens, cached vs. uncached, interactive vs. offline. In most products 10-20% of call sites cause 80% of spend. Often one agent loop re-sends a 30k-token context on every step.
  - **What does "quality" mean here?** Task success rate, human preference win-rate, a downstream business KPI (resolution rate, thumbs-down rate), or all three? Which slices must not regress (enterprise tenants, safety-critical flows)?
  - **API or self-hosted?** On an API, the levers are tokens, model choice, caching and batch. On your own GPUs, you also have utilization, batching, quantization and hardware choice.
  - **What latency SLOs constrain us?** Batch and aggressive cascades both add latency.
#### Step 0: Build a cost model and a quality gate
  - Instrument every call with: feature, tenant, model, input/output/cached tokens, latency, and an outcome signal. Then cost per *successful task*, not per call, becomes the north-star metric.
  - Build a frozen eval set of roughly 1-3k real production samples, stratified by feature and difficulty. Score it with task-specific checks plus a calibrated LLM judge (judge agreement with humans ≥ 0.8 on a spot-checked subset). The guardrail is a non-inferiority test: quality drop \< 1 pt absolute at 95% confidence, overall *and* on each critical slice.
#### Lever 1: Prompt/prefix caching (often 30-60% of input cost)
  - Restructure prompts as **static → semi-static → dynamic**: system prompt, tool schemas and few-shot examples first, then retrieved documents, then the user turn. Provider prompt caching bills cache reads at a small fraction of base input price (Anthropic: 0.1x for most models, writes at 1.25x for a 5-min TTL). OpenAI applies discounted caching automatically for long prefixes.
  - For chat and agents, where the conversation prefix is re-sent on every turn, cache hit rates of 70-90% of input tokens are realistic. Input is usually 70-90% of tokens in RAG and agent workloads, so this alone can halve the bill.
  - Self-hosted equivalent: vLLM automatic prefix caching or SGLang RadixAttention. Here the saving is avoided prefill compute and higher throughput.
#### Lever 2: Model routing / cascades (often 40-60% of the remaining spend)
  - Price gaps between model tiers are 5-30x. If 60-70% of traffic is "easy" (classification, extraction, short FAQ), a learned router or a cascade (cheap model first, escalate on low confidence or a failed verifier) keeps quality within noise. FrugalGPT reported large cost reductions at matched accuracy, and RouteLLM reported more than 2x cost reduction on MT-Bench without quality loss.
  - Distill the highest-volume narrow tasks into a fine-tuned small model using big-model outputs as labels. A fine-tuned small model often *beats* a prompted frontier model on a narrow task, at 10-50x lower cost.
#### Lever 3: Batch and async (50% off eligible traffic)
  - Evals, nightly enrichment, embeddings backfills and summarization pipelines go to batch APIs (Anthropic and OpenAI both price batch at about 50% off, with up to 24h turnaround). This discount stacks with caching.
#### Lever 4: Token hygiene (10-30%)
  - **Output tokens cost 3-5x input tokens.** Cap max\_tokens, require structured/terse output, and stop asking for chain-of-thought where the task does not benefit. With reasoning models, set the thinking budget per task.
  - **Retrieve less, retrieve better.** Moving from top-20 to top-5 chunks with a reranker often *improves* quality and cuts context by 60-75%.
  - Summarize or compact long conversation history. Remove tool schemas the current step cannot use. Use prompt compression (LLMLingua-style) only where measured.
  - Deduplicate requests: retries, double-submits, and the same prompt sent by many users (exact-match cache).
#### Lever 5 (self-hosted): Serving efficiency
  - Continuous batching, FP8/INT4 weight quantization (AWQ/GPTQ), speculative decoding, and right-sizing the GPU SKU. Moving from 30% to 70% utilization roughly halves cost per token.
#### Worked example
$1M/month baseline → caching (-40% → $600k) → route 65% of traffic to a 10x-cheaper tier (-55% → $270k) → batch 20% of the remainder (-10% → $243k) → token trimming (-15% → about $205k). The result is a \~80% reduction, which leaves headroom for the escalation rate turning out higher than planned.
#### Measuring success
  - Cost per successful task, cache-hit token ratio, router escalation rate, and p50/p95 latency.
  - Quality: offline non-inferiority on the frozen set, then an online A/B on the business KPI with a 1-5% holdout kept on the old stack for weeks to catch slow drift.
  - Per-slice dashboards. Averages hide the long-tail tenant whose quality dropped 8 points.
### Tradeoffs
|  |  |  |  |
| :- | :- | :- | :- |
| **Option** | **Pros** | **Cons** | **When to choose** |
| Prompt/prefix caching | Near-zero quality risk; large input savings; also cuts TTFT | Requires prompt restructuring; TTL misses; write premium | Always, first. Long shared prefixes, chat, agents |
| Routing/cascade | Biggest lever when traffic is heterogeneous | Router errors cause silent quality loss; cascades add latency for hard queries | Mixed difficulty, high volume |
| Distill/fine-tune small model | 10-50x cheaper per call; often higher quality on narrow tasks | Training and maintenance cost; staleness when the task drifts | Stable, high-volume, narrow tasks |
| Batch API | 50% off with zero quality change | Hours of latency | Offline and async work |
| Token trimming / compression | Cheap to do; often improves quality | Aggressive compression drops key facts | Bloated RAG or agent contexts |
| Self-host + quantize | Lowest marginal cost at scale | Ops burden; quantization regressions on long-tail tasks | More than \~$1-2M/yr steady load on open-weight-capable tasks |

  - Sequence by risk: zero-quality-risk levers (caching, batch, dedup) first, quality-risk levers (routing, distillation, quantization) second, each behind its own flag.
  - Optimize cost per *successful* outcome. A cheaper model that causes more retries or human escalations can cost more end to end.
### Pitfalls interviewers probe
  - **Breaking cache prefixes by accident.** A timestamp, request ID or non-deterministically ordered tool list near the top of the prompt drops the hit rate to zero. Monitor cached-token ratio as a first-class metric.
  - **Eval set not representative.** Validating routing on easy samples and then shipping to a heavy tail. Stratify the set and test per slice.
  - **LLM-judge bias.** Judges favor longer and more fluent outputs and their own model family. Calibrate against human labels and check judge-human agreement on the slices being changed.
  - **Ignoring output tokens and reasoning tokens.** Teams optimize input while a thinking model burns 5k hidden tokens per call.
  - **Second-order costs.** Lower quality raises retries, support tickets and churn. Count those.
  - **No rollback or holdout.** Without a persistent holdout you cannot detect slow quality drift after the launch A/B ends.
### Sources and further reading
  - [FrugalGPT (Chen, Zaharia, Zou, 2023)](https://arxiv.org/abs/2305.05176): LLM cascades, prompt adaptation and approximation for large cost cuts at matched accuracy.
  - [RouteLLM (Ong et al., 2024)](https://arxiv.org/abs/2406.18665): learned routers trained on preference data; more than 2x cost reduction without quality loss.
  - [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching): cache pricing multipliers, TTLs, minimum cacheable lengths, breakpoints.
  - [Anthropic Message Batches API](https://platform.claude.com/docs/en/build-with-claude/batch-processing): 50% batch discount that stacks with caching.
  - [OpenAI prompt caching guide](https://platform.openai.com/docs/guides/prompt-caching): automatic prefix caching behavior and how to structure prompts for it.
  - [LLMLingua (Jiang et al., 2023)](https://arxiv.org/abs/2310.05736): prompt compression with small-model perplexity filtering.
  - [Distilling Step-by-Step (Hsieh et al., 2023)](https://arxiv.org/abs/2305.02301): small distilled models outperform much larger LLMs on narrow tasks.
  - [vLLM / PagedAttention (Kwon et al., 2023)](https://arxiv.org/abs/2309.06180): the serving-efficiency foundation for self-hosted cost cuts.
## Q7. Cut first-token latency for a chat app
### Short answer
Time-to-first-token (TTFT) is network, plus queueing, plus prefill, plus whatever runs before the model is even called (auth, retrieval, guardrails). So I first decompose p50/p95 TTFT into those stages and attack the largest one. Usually that means: running pre-model work in parallel and streaming from the edge, prefix/KV caching so the long system prompt and conversation history are not re-prefilled, keeping prefill from being starved by decode (chunked prefill or disaggregation), and tighter admission control so requests do not queue. A typical result is p95 TTFT going from 2-3 s to 300-600 ms, without touching the model.
### Detailed answer
#### Clarify first
  - **p50 or p95/p99?** Tail TTFT is usually driven by queueing and long prompts, not average prefill speed.
  - **Hosted API or our own serving stack?** On an API, the controls are prompt shape, caching, region, model choice and pipeline. Self-hosted, the scheduler and hardware are also in scope.
  - **Typical prompt length?** For 500 tokens prefill is about 20-50 ms. For 30k tokens of history plus RAG it is 1-3 s on an H100-class GPU for a 70B model, and that changes everything.
  - **What must happen before the first token?** Moderation, retrieval, tool planning? Can the first visible token be something other than the final answer's first token?
#### Step 1: Measure the waterfall
Trace every request with spans: client → edge → auth → retrieval → prompt build → queue wait → prefill → first token → network back. A typical unoptimized breakdown at p95:
  - Network/TLS: 100-200 ms (cross-region)
  - Pre-model work: 300-800 ms (embedding + vector search + rerank + moderation, often run in sequence)
  - Queue wait: 0-1500 ms (bursty load, no headroom)
  - Prefill: 200-2000 ms (scales with prompt length) Report TTFT *as the user perceives it* (from client send to first rendered token), not just server-side.
#### Step 2: Remove pre-model latency
  - **Parallelize.** Run moderation alongside retrieval, or alongside generation with output gating. Run retrieval in parallel with intent classification.
  - **Speculative retrieval.** Start embedding the query as the user types or on submit. Cache embeddings for frequent queries.
  - **Skip retrieval when it is not needed.** A cheap classifier or heuristic for chit-chat and follow-ups.
  - Use a fast reranker (a small cross-encoder at about 20 ms) or drop reranking for latency-critical paths.
#### Step 3: Make prefill cheaper or avoid it
  - **Prefix/KV caching.** Keep the system prompt and conversation history byte-stable so turn N reuses the KV cache from turn N-1. Only the new user message is prefilled. On an API this is prompt caching (Anthropic reports TTFT reductions of up to \~85% for long cached prompts). Self-hosted, use vLLM automatic prefix caching or SGLang RadixAttention, plus **session-affinity routing** so a conversation returns to the replica that holds its KV.
  - **Shorter prompts.** Compact old turns into summaries, retrieve fewer and better chunks, and load tool schemas lazily.
  - **Hardware and parallelism.** Prefill is compute-bound, so tensor parallelism across more GPUs and FP8 cut prefill time nearly linearly.
#### Step 4: Fix scheduling (self-hosted)
  - **Chunked prefill** (Sarathi-Serve). Split long prefills into chunks mixed into decode batches so a 30k-token prompt does not stall everyone else's tokens, and so new requests get scheduled quickly.
  - **Prefill/decode disaggregation** (DistServe, Splitwise). Separate pools with KV transfer let you tune for TTFT and inter-token latency independently. Worth it at large scale with long prompts.
  - **Admission control and headroom.** Queueing delay grows sharply past about 70-80% utilization. Autoscale on queue depth and TTFT, not on GPU utilization. Use priority classes: interactive chat ahead of batch.
  - Keep warm replicas. Model load on a cold start takes tens of seconds to minutes and must never be on the request path.
#### Step 5: Network and client
  - Use streaming (SSE or WebSocket) with HTTP/2 or 3, keep-alive connections, regional endpoints near users, and no buffering proxies. Nginx proxy\_buffering silently kills streaming.
  - Pre-warm the connection when the chat input gets focus.
#### Step 6: Perceived latency
  - Show a skeleton or "thinking" state at once. For reasoning models, stream a short status ("Searching your docs...") while the hidden reasoning runs.
  - For simple turns, route to a smaller and faster model (see Q9).
#### Model-level options
Speculative decoding (Medusa, EAGLE) mainly improves *inter-token* latency, not TTFT. Say this explicitly; it is a common confusion. Smaller or distilled models and quantization improve both.
#### Measuring success
  - p50/p95/p99 TTFT by prompt-length bucket and region, plus inter-token latency (TPOT). Goodput means requests that meet *both* the TTFT and TPOT SLOs.
  - Load-test with production-shaped arrival processes (bursty, heavy-tailed prompt lengths), not uniform synthetic load.
  - Link TTFT to an engagement metric through an A/B test (abandonment, messages per session) to justify the GPU cost of headroom.
### Tradeoffs
|  |  |  |  |
| :- | :- | :- | :- |
| **Option** | **Pros** | **Cons** | **When to choose** |
| Prefix/KV caching + session affinity | Large TTFT cut on multi-turn chats; also saves compute | Affinity hurts load balance; KV memory pressure evicts other work | Multi-turn chat, long system prompts |
| Chunked prefill | Smooths tail TTFT and TPOT; simple to enable | Slightly lower peak throughput; chunk size needs tuning | Mixed prompt lengths on shared replicas |
| Prefill/decode disaggregation | Tune each SLO independently; best goodput at scale | KV transfer bandwidth (needs a fast interconnect); operational complexity | Large fleets, long prompts, strict SLOs |
| Overprovision headroom | Kills queueing tail directly | Expensive idle GPUs | Latency-critical consumer chat |
| Smaller/faster model | Cuts everything | Quality risk | Easy turns via a router |
| Parallelize pre-model work | Cheap and often the biggest win | Wasted work when results are discarded | Always |

  - The core judgment is the cost-latency curve. Running at 60% utilization rather than 85% may double cost per token but cut p99 TTFT by 5x. Decide with product, using engagement data.
  - Session affinity and load balancing conflict. Use consistent hashing with bounded load and fall back to recompute.
### Pitfalls interviewers probe
  - **Optimizing mean instead of p95/p99.** The tail is queueing plus long prompts, and the mean hides both.
  - **Thinking speculative decoding fixes TTFT.** It speeds up decode. TTFT is prefill and queueing.
  - **Cache-busting prompts.** Timestamps, randomized few-shot order, or per-user content placed before shared content. Each one forces a full prefill.
  - **Measuring server-side only.** Buffering proxies, client rendering and TLS handshakes can add hundreds of ms that server metrics never see.
  - **Autoscaling on GPU utilization.** It lags, and utilization is high even when TTFT is fine. Scale on queue depth and TTFT SLO burn.
  - **Safety gates added in series.** Each sequential guardrail adds 100-300 ms. Run them in parallel or stream-gated.
### Sources and further reading
  - [Sarathi-Serve (Agrawal et al., 2024)](https://arxiv.org/abs/2403.02310): chunked prefill and stall-free batching for the throughput-latency tradeoff.
  - [DistServe (Zhong et al., 2024)](https://arxiv.org/abs/2401.09670): disaggregating prefill and decode to optimize goodput under TTFT/TPOT SLOs.
  - [vLLM / PagedAttention (Kwon et al., 2023)](https://arxiv.org/abs/2309.06180): KV-cache memory management behind modern serving.
  - [vLLM Automatic Prefix Caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching.html): how prefix KV reuse works in vLLM.
  - [SGLang / RadixAttention (Zheng et al., 2023)](https://arxiv.org/abs/2312.07104): radix-tree KV cache reuse across requests.
  - [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching): API-level prefix caching for lower latency and cost.
  - [Medusa (Cai et al., 2024)](https://arxiv.org/abs/2401.10774): decode-side acceleration, useful to contrast with TTFT work.
## Q8. Design a semantic cache with hit-rate tracking
### Short answer
A semantic cache embeds each normalized request, looks for a nearest neighbor above a similarity threshold within the same scope (tenant, model, prompt version, context fingerprint), and returns the stored response, skipping the LLM call. The hard parts are deciding when to cache, not running the vector search: you need a per-domain threshold tuned on labeled pairs, a verification step for borderline matches, and strict invalidation and isolation. For tracking, I measure exact-hit, semantic-hit and miss rates, and also the *false-hit rate* from sampled audits, because a cache at 30% hit rate with 5% wrong answers is a quality incident, not a cost saving.
### Detailed answer
#### Clarify first
  - **Is the traffic actually repetitive?** FAQ and support bots often see 20-40% near-duplicates. Open-ended multi-turn chat is often under 5%. Run an offline replay on a week of logs before building anything.
  - **Are responses context-dependent?** Personalized, time-sensitive or RAG-over-changing-data responses are dangerous to share.
  - **What does a wrong hit cost?** Customer-facing medical or financial answers compared with internal search suggestions.
  - **What is the latency budget for the lookup itself?** It should be under 10-20 ms so that misses are not penalized.
#### Architecture
1.  **Normalize and scope.** Lowercase, strip whitespace, canonicalize numbers and dates where safe. Build the **scope key** = hash(tenant, model ID, system prompt version, tool set, locale, and any user-specific context such as auth role). Cache lookups never cross scopes.
2.  **Exact layer first.** Hash(scope, normalized prompt) in Redis. It costs under 1 ms, has no false hits, and often catches 5-15% (retries, popular queries).
3.  **Semantic layer.**
      - Embed only the *semantic part* (the last user turn, plus a short summary of prior turns if it is multi-turn) with a small fast embedding model (about 5-15 ms on CPU/GPU, 384-1024 dims).
      - ANN search (HNSW in a vector DB or FAISS) filtered by scope key, top-k = 3-5.
      - Accept if cosine ≥ τ\_high (for example 0.95). Treat τ\_low ≤ sim \< τ\_high as **borderline**: optionally verify with a cross-encoder or a small LLM judge ("Do these two questions have the same answer?") at about 30-80 ms, still far cheaper than generation.
      - Below τ\_low, it is a miss.
4.  **On a miss**, call the LLM, then **decide whether to write**. Skip writing for responses that contain user-specific data, tool calls with side effects, low-confidence or refusal outputs, or very long tail-unique queries. Store {embedding, normalized query, response, scope, model version, created\_at, source doc versions, ttl, hit\_count}.
5.  **Invalidation.** TTL by content class (hours for news, days or weeks for stable FAQ). Event-driven purge when source documents change (store doc IDs/versions with each entry). Flush everything on a model or prompt version bump (it is in the scope key, so this is automatic).
6.  **Eviction.** LRU/LFU with size caps. Hit distributions are Zipfian, so a few hundred thousand entries usually capture most of the value.
#### Threshold tuning
  - Build a labeled set of query pairs from logs: about 2-5k pairs scored "same answer / different answer" by humans or a strong judge, with hard negatives included ("cancel my order" vs. "cancel my subscription"; "flights to Paris in May" vs. "...in March").
  - Plot precision versus hit rate as τ varies, and pick τ to meet a target **false-hit rate**, for example ≤ 0.5% for customer-facing traffic. Thresholds are domain-specific and should be set per route or intent, not globally. Recent work (vCache) learns per-entry thresholds with error-rate guarantees.
#### Hit-rate tracking (the observability design)
Emit an event for every lookup: {scope, layer: exact|semantic|verified|miss, similarity, latency, entry\_age, entry\_id}. Dashboards:
  - **Hit rate** by layer, tenant and intent. Track it both by request and by **cost saved** (tokens avoided × price), because hits on short prompts save little.
  - **Similarity histogram** of accepted hits, to watch mass drifting toward the threshold.
  - **False-hit rate.** Sample about 1% of semantic hits, regenerate fresh in shadow, and have a judge compare. Also log user signals (regenerate clicks, thumbs-down) on hit responses versus miss responses. Alert if hits get worse feedback than misses.
  - **Cache efficiency.** Entries written versus ever hit (often 80%+ are never reused, which argues for write-admission policies), hit-count distribution, eviction rate.
  - **Latency.** Lookup p99, plus the end-to-end latency win on hits (often 1-5 s down to about 50 ms).
  - **Offline replay harness.** Replay logs against new thresholds or embedding models to predict hit rate and false hits before deploying.
#### Expected numbers
FAQ/support: 20-40% combined hit rate, false hits \< 1% with verification. General assistant: 3-10%. For general chat, provider prompt caching usually saves more money than semantic caching does. Say so.
### Tradeoffs
|  |  |  |  |
| :- | :- | :- | :- |
| **Option** | **Pros** | **Cons** | **When to choose** |
| Exact-match cache only | Zero false hits; trivial | Low hit rate on free text | Always as layer 1; templated or programmatic traffic |
| Semantic, fixed global threshold | Simple; good hit rate | Wrong-answer risk varies by domain | Prototypes, low-stakes domains |
| Semantic + verifier for borderline | High precision at decent recall | Extra 30-80 ms and cost on borderline lookups | Customer-facing, moderate stakes |
| Per-intent / learned thresholds | Best precision-recall frontier | Needs labeled data and maintenance | Mature, high-volume deployments |
| Provider prefix caching instead | No correctness risk; works for any repeated prefix | Saves input tokens only, not the generation | Long shared prompts, unique questions |
| Cache retrieval results, not answers | Safer; the answer stays fresh and personalized | Smaller savings | Personalized or time-sensitive answers |

  - The real decision is the tolerated false-hit rate. Set it from the cost of a wrong answer, then let it determine τ and the hit rate. Do not start from a target hit rate.
  - Isolation beats hit rate. Never share entries across tenants or permission levels, even if that halves the hit rate.
### Pitfalls interviewers probe
  - **Embedding similarity is not answer equivalence.** Negations, entities, dates and numbers ("2023 revenue" vs. "2024 revenue") embed nearly identically. Use hard-negative evals and entity/number checks.
  - **Cross-tenant or cross-user leakage.** A cached answer containing user A's data served to user B is a security incident. Scope keys and write-admission rules are mandatory.
  - **Multi-turn context.** "What about the second one?" means different things in different conversations. Embedding only the last turn causes false hits.
  - **Stale answers** after document, price or policy changes, or after a model or prompt upgrade. Version everything in the key or the metadata.
  - **Measuring only hit rate.** Without false-hit audits and the cost-weighted hit rate you cannot tell whether the cache helps.
  - **Lookup overhead on misses.** At a 5% hit rate, adding 30 ms to 95% of requests may be a net loss.
### Sources and further reading
  - [GPTCache (Zilliz, GitHub)](https://github.com/zilliztech/GPTCache): open-source semantic cache with pluggable embedding, storage, and similarity evaluation.
  - [vCache: Verified Semantic Prompt Caching (2025)](https://arxiv.org/abs/2502.03771): learned per-entry thresholds with user-defined error-rate guarantees.
  - [MeanCache (Gill et al., 2024)](https://arxiv.org/abs/2403.02694): user-centric semantic caching, with analysis of false hits and context-dependent queries.
  - [Sentence-BERT (Reimers and Gurevych, 2019)](https://arxiv.org/abs/1908.10084): the standard bi-encoder embedding approach behind most semantic caches.
  - [HNSW (Malkov and Yashunin, 2016)](https://arxiv.org/abs/1603.09320): the ANN index used by most vector stores.
  - [FAISS: Billion-scale similarity search with GPUs (Johnson et al., 2017)](https://arxiv.org/abs/1702.08734): the vector search library for self-managed ANN.
  - [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching): the complementary, zero-risk prefix caching layer.
## Q9. Route requests between a cheap and a smart model
### Short answer
I'd frame routing as a cost-quality optimization: send each request to the cheapest model whose expected quality is within tolerance of the strong model's. In practice, a learned router predicts P(cheap model's answer is as good as the strong one's) and compares it against a threshold tuned to a cost or quality target. I'd add cascade-style escalation when the cheap model's output fails a verifier. The router is trained on our own traffic, labeled by comparing both models' outputs, and success is measured as the quality-cost curve (for example, 95% of the strong model's quality at 30-40% of its cost), not router accuracy. Production also needs hard rules (tenant tier, safety-sensitive intents), calibration monitoring, and a shadow-evaluated holdout, because the traffic mix drifts.
### Detailed answer
#### Clarify first
  - **What is the cost and latency gap between the models?** 10x price and 3x latency gives a lot of room. 2x gives very little.
  - **Quality metric and tolerance?** "Non-inferior within 1 pt on task success" vs. "win-rate ≥ 48% vs. strong-only".
  - **How heterogeneous is the traffic?** If 90% of queries are hard, routing cannot help much. Measure first: run both models on a sample and compute the fraction where the cheap model is as good. That fraction is the ceiling on savings.
  - **Is per-request latency budget available for cascades?** Cascades spend the cheap call's latency on every escalated request.
  - **Same provider/model family?** That matters for prompt compatibility and for prefix caching (switching models loses the cache).
#### Router designs (from simplest to strongest)
1.  **Rules / intent-based.** A route table by feature or intent ("classification → cheap; code generation → strong"). Transparent and a good baseline. Often captures 50% of the savings.
2.  **Learned pre-generation router.** A small classifier (fine-tuned BERT-class encoder, or embedding + MLP/kNN) on the prompt, plus features (length, conversation depth, tool count, tenant tier). Output: P(cheap is good enough). Inference takes 2-10 ms. RouteLLM-style training on preference data (Chatbot Arena plus augmentation) works well, and matrix-factorization and BERT routers both generalize reasonably.
3.  **Cascade (post-generation).** Call the cheap model, score its output (self-consistency agreement across 2-3 samples, a verifier model, token log-prob confidence, schema/test validation for code or JSON), and escalate if the score is low. FrugalGPT and AutoMix-style approaches. Higher precision, but escalated requests pay twice and take longer.
4.  **Hybrid.** The router sends clearly hard requests straight to the strong model, clearly easy ones to the cheap model, and the uncertain middle band through the cascade.
#### Building the training data
  - Sample 20-50k production prompts, stratified. Run both models. Label with an LLM judge (pairwise, both orderings to cancel position bias) plus programmatic checks where available. About 1-2k get human labels to calibrate the judge.
  - Target: y = 1 if cheap ≥ strong (or within margin). Include **hard negatives**, short prompts that are deceptively hard ("prove this", "fix this bug").
  - Retrain monthly or on drift. Both models change underneath you when providers update them.
#### Choosing the threshold
  - Sweep the threshold and plot quality vs. % routed to the strong model (the deferral curve). Pick an operating point such as "85% of the strong model's win-rate at 25% strong calls". Report **APGR** (average performance gap recovered) or call-performance-threshold metrics, as RouteLLM does.
  - Set per-slice thresholds where slices differ (enterprise tenants get a more conservative threshold).
#### Serving architecture
  - The router runs in the gateway (about 5 ms budget). Hard overrides come first: safety-sensitive intents, paid tier, explicit user model choice, long-context requirements, tool sets the cheap model handles poorly.
  - **Stickiness within a conversation.** Switching models mid-conversation breaks prefix caching and can cause style or persona whiplash. Route per conversation, or only escalate upward.
  - A fallback path: on cheap-model errors, timeouts or refusals, retry on the strong model.
  - Log the decision, router score, chosen model and outcome for every request.
#### Measuring and monitoring
  - **Offline:** the deferral curve on a held-out set; calibration (reliability diagram, ECE) of the router score.
  - **Online:** A/B of routed vs. strong-only, with the business KPI and regenerate/thumbs-down rates per arm. Keep a permanent **1-2% shadow slice** where both models run, to estimate the router's live false-easy rate.
  - **Drift alarms:** the fraction routed to cheap changing more than X% week over week, a shift in score distribution, or a rising escalation rate.
  - **Expected outcome:** for typical assistant traffic, 50-80% routed cheap, total cost down 40-70%, and quality within noise on aggregate metrics. Then verify the long tail separately.
### Tradeoffs
|  |  |  |  |
| :- | :- | :- | :- |
| **Option** | **Pros** | **Cons** | **When to choose** |
| Static rules by feature/intent | Transparent, zero latency, easy to debug | Coarse; misses within-intent difficulty | Starting point; clearly separated features |
| Learned pre-generation router | One call per request; ms overhead; fine-grained | Needs labeled data; silent errors; drifts | High volume, heterogeneous difficulty |
| Cascade with verifier | High precision; uses actual output quality | Escalated requests pay \~2x cost and latency | Verifiable tasks (code, JSON, math), relaxed latency |
| Hybrid router + cascade band | Best cost-quality frontier | Most complex system | Mature, large-scale deployments |
| Always strong model | Simplest, max quality | Highest cost | Low volume or very high stakes |

  - **Asymmetric errors.** Routing a hard query to the cheap model (false-easy) hurts users. Routing an easy query to the strong model only wastes money. Tune for a false-easy budget, not for accuracy.
  - **Where does the router's value come from?** If a simple length or intent rule gets 80% of the gain, ship that and spend the effort elsewhere.
### Pitfalls interviewers probe
  - **Optimizing router accuracy instead of the cost-quality curve.** A 90%-accurate router can still be worse than a rule if its errors land on high-value queries.
  - **Label leakage and judge bias.** A judge that favors longer answers makes the strong model look better everywhere and teaches the router to never route cheap.
  - **Mid-conversation model switching.** It breaks prompt caching (costing more), changes tone, and the cheap model may not follow context the strong model established.
  - **Model updates invalidate the router.** A provider silently improving the cheap model means you are under-routing to it. Re-label regularly.
  - **Cascade latency.** p95 latency for escalated requests is cheap + strong. Product may not accept it for chat.
  - **Adversarial or gaming behavior.** Users learn that "this is very important and complex" gets the strong model. Watch for prompt-feature exploitation.
### Sources and further reading
  - [RouteLLM (Ong et al., 2024)](https://arxiv.org/abs/2406.18665): learned routers from preference data; deferral curves and APGR metrics.
  - [FrugalGPT (Chen, Zaharia, Zou, 2023)](https://arxiv.org/abs/2305.05176): LLM cascades with a learned answer scorer.
  - [Hybrid LLM (Ding et al., ICLR 2024)](https://arxiv.org/abs/2404.14618): quality-aware routing between small and large models with a tunable quality threshold.
  - [Anthropic: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents): describes routing as a core workflow pattern and when to use it.
  - [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching): why model stickiness matters for cache reuse.
  - [Distilling Step-by-Step (Hsieh et al., 2023)](https://arxiv.org/abs/2305.02301): making the "cheap" model better on your traffic, which widens the routable fraction.
## Q10. Build an agent that uses tools reliably
### Short answer
Tool-use reliability is mostly a systems property, not a prompt property. I'd make the tools hard to misuse: few, well-named tools with strict schemas, informative errors and idempotent side effects. I'd make the loop robust: schema-constrained calls, validation, bounded retries with error feedback, step and budget limits, and human confirmation for irreversible actions. And I'd measure end-to-end task success, with multi-trial pass^k, on a realistic eval suite with simulated users and real tool backends. The single biggest lever is usually the tool interface itself: consolidating overlapping tools, returning concise high-signal results, and writing descriptions the way you would for a new engineer.
### Detailed answer
#### Clarify first
  - **What does "reliably" mean?** Per-call schema validity (easy, about 99%+ with strict mode) vs. task success (hard, often 50-80% on realistic multi-step tasks) vs. *consistency* across retries (τ-bench showed pass^8 far below pass^1).
  - **How many tools, how many steps, read-only or side-effecting?** Ten tools and 3 steps is a different problem from 200 tools and 50 steps.
  - **What is the cost of a wrong action?** Searching a doc vs. issuing a refund vs. running rm -rf.
  - **Latency and cost budget per task?** That bounds the number of steps and retries.
#### Layer 1: Tool design (the highest-leverage layer)
  - **Fewer, higher-level tools.** Use schedule\_meeting(attendees, window), not list\_users + get\_calendar + find\_slot + create\_event. Every extra tool adds selection errors and context tokens. With more than about 20-30 tools, use dynamic tool loading or search over tool descriptions.
  - **Clear names, namespacing and descriptions**, with examples, units, formats and when *not* to use the tool. Use unambiguous parameter names (user\_id, not user) and enums instead of free strings.
  - **Strict schemas.** JSON Schema with required fields and enums. Enable provider strict/structured-output modes so calls always parse.
  - **Agent-friendly responses.** Concise, semantically meaningful fields (names rather than UUIDs where possible), pagination and truncation with hints ("showing 20 of 340; refine with query"). Keep responses to about 1-5k tokens max.
  - **Actionable errors.** "date must be ISO-8601 like 2026-10-15; got '10/15'", not a stack trace. Errors are the model's main signal for self-correction.
  - **Idempotency keys and dry-run modes** for side-effecting tools, so retries cannot double-charge.
#### Layer 2: The control loop
  - Use a ReAct-style loop (reason → call → observe) with the model deciding, but wrap it in deterministic guards:
      - **Validate** every call against the schema and business rules before executing (permissions, value ranges, allowed resources). On failure, return the error to the model without executing.
      - **Bounded retries:** 2-3 per call with the error in context, then escalate or abort.
      - **Step, token and time budgets** (for example max 25 steps, $X, 120 s), with loop detection (the same call with the same arguments repeated more than 2 times).
      - **Parallel calls** for independent reads, to cut latency.
  - **Context management for long tasks:** compact old tool outputs, keep a scratchpad or to-do list, and use sub-agents for large searches so the main context stays clean.
  - **Prefer workflows where you can.** If the path is known, hard-code the sequence (prompt chaining or routing) and use the LLM only for the fuzzy steps. Reserve fully autonomous loops for open-ended tasks.
#### Layer 3: Safety and permissions
  - Classify tools as read, reversible-write and irreversible. Require **human confirmation** or policy approval for irreversible actions.
  - Least-privilege credentials scoped per user and session. Never give the model raw admin tokens.
  - **Prompt-injection defense:** treat tool outputs (web pages, emails, docs) as untrusted data. Do not let content from them trigger privileged tools without confirmation. Separate the planner's privileges from the reader's (dual-LLM or quarantined patterns). Log and alert on anomalous tool sequences.
  - Sandbox code execution (containers or gVisor, no network by default, CPU/memory/time limits).
#### Layer 4: Evaluation
  - **Tool-level unit evals:** for each tool, prompts where it should and should not be called; check argument correctness. BFCL-style AST and executable checks.
  - **Task-level evals:** 100-500 realistic multi-step tasks with *verifiable end states* (database state matches expected, test suite passes), not judged transcripts alone. Include simulated users (as τ-bench does) for multi-turn clarification.
  - **Report pass@1 and pass^k** (succeeds on all k trials) for reliability, plus cost, steps and latency per task.
  - **Failure taxonomy** from transcript review: wrong tool, wrong arguments, hallucinated tool or argument, premature stop, looping, ignored error, policy violation. Fix the top category, re-run, repeat. Use an agent to analyze failed transcripts and propose tool-description fixes (Anthropic's tool-writing guidance describes this loop).
  - **Production:** trace every step (OpenTelemetry-style spans), track task completion, user intervention rate, error rate per tool, and auto-sample transcripts for review.
#### Concrete targets
Schema-valid calls ≥ 99.5% (strict mode makes this nearly 100%). Tool-selection accuracy ≥ 95% on the unit suite. Task success from 60% to 85%+ through tool redesign and error-message work. Zero unconfirmed irreversible actions. Median steps per task trending down.
### Tradeoffs
|  |  |  |  |
| :- | :- | :- | :- |
| **Option** | **Pros** | **Cons** | **When to choose** |
| Fixed workflow (chained calls) | Predictable, testable, cheap | Brittle to unexpected inputs; no adaptivity | Known, repeatable processes |
| Autonomous ReAct-style agent | Handles open-ended tasks; adapts to errors | Variance, cost, harder to evaluate | Open-ended, exploratory tasks |
| Many fine-grained tools | Flexible, easy to build from existing APIs | Selection errors, context bloat, long chains | Rarely. Prototypes only |
| Few consolidated tools | Higher success, fewer steps | More engineering per tool | Production agents |
| Human-in-the-loop on writes | Safety, user trust | Friction and latency | Irreversible or high-value actions |
| Fine-tune for tool use | Better selection and arguments on your API | Data and maintenance cost; lags base-model upgrades | Very high volume, stable tool set |

  - **Autonomy vs. control:** add autonomy only where evals show it raises task success. Each extra degree of freedom adds variance.
  - **Reliability compounds.** At 95% per step, a 20-step task succeeds about 36% of the time. Reducing the step count (better tools) often beats improving per-step accuracy.
### Pitfalls interviewers probe
  - **Equating valid JSON with reliability.** Strict mode solves parsing, but selecting the right tool, using correct arguments and knowing when to stop are where tasks fail.
  - **Single-run evals.** pass@1 hides inconsistency. Agents can pass a task once and fail it 40% of the time. Report pass^k.
  - **Verbose tool outputs flooding context.** Dumping 50k tokens of raw API JSON degrades reasoning and cost. Summarize, paginate and filter.
  - **Non-idempotent retries.** Retrying a timed-out create\_payment without an idempotency key double-charges.
  - **Prompt injection through tool results.** A retrieved web page or email instructing the agent to exfiltrate data via another tool. The model alone is not a sufficient defense; permissions and confirmation gates are.
  - **No stop condition.** Infinite loops, repeated identical calls, or an agent "finishing" without verifying the end state. Budgets plus explicit success checks are needed.
