## Q1. Design a RAG system for 10M documents
### Short answer
I'd build it as a retrieval system first and a generation system second. Most failures show up there, and it is also the part you can measure cheaply. Concretely: an offline pipeline that parses, chunks (\~50-100M chunks), enriches and embeds documents into a sharded ANN index plus a BM25 index. An online path does query understanding, then hybrid retrieval (top \~200), then cross-encoder reranking (top \~10-20), then grounded generation with citations. ACLs and freshness are enforced inside the index, never after the fact. Before I pick components I'd pin down the SLOs (p95 latency, cost per query, freshness, recall@k targets) and build a labeled eval set. Every other decision gets judged against those numbers.
### Detailed answer
#### Clarifying questions (they change the design)
  - **What are the documents?** Average length, formats (PDF/HTML/scans), languages, and how much is tables or code. 10M docs of \~5 pages each comes to \~25B tokens, a very different system from 10M tweets.
  - **Query mix:** factoid lookup, multi-hop synthesis, or "find all X"? Exhaustive-recall queries need different machinery (filters, aggregation, agentic search) than top-k QA.
  - **QPS and latency SLO:** say 50 QPS at peak with p95 under 3s end to end, and time-to-first-token under 1.5s.
  - **Freshness:** what update rate (say 1%/day = 100k docs/day), and how quickly must a new doc be searchable (minutes or hours)?
  - **Access control:** per-user or per-tenant ACLs? This decides whether filtering happens pre-ANN or post-ANN, and it is the most common reason RAG systems leak data.
  - **Cost envelope and hosting constraints:** VPC-only, which model providers are allowed, data residency.
#### Offline / ingestion pipeline
1.  **Parse:** layout-aware parsing (PDF to structured blocks, OCR for scans, tables kept as Markdown/HTML). Parsing quality is the hidden ceiling on everything downstream. I'd sample about 200 docs and eyeball the output before tuning anything else.
2.  **Chunk:** structure-aware, \~300-800 tokens with headings carried as metadata, giving \~5-10 chunks/doc, so **50-100M chunks**. Store a parent pointer so you can expand small-to-big at read time.
3.  **Enrich:** title, section path, doc date, ACL principals, tenant, language, doc type. Optionally prepend an LLM-generated context sentence per chunk (Anthropic's "contextual retrieval"). Anthropic reports \~35% fewer retrieval failures from contextual embeddings alone, and up to \~67% with contextual BM25 plus reranking. With prompt caching the one-time cost is roughly $1 per million document tokens, so it is affordable at this scale.
4.  **Embed:** an off-the-shelf model from the MTEB leaders, fine-tuned later on in-domain pairs. Sizing: 100M chunks × 1024 dims × 4 bytes is **\~410 GB in fp32**. Matryoshka truncation to 512 dims plus int8 brings that to \~51 GB, and binary/PQ codes bring it to \~6-13 GB with an fp16/int8 rescoring pass. Embedding throughput: 25B tokens on a few dozen GPUs is about a day. Budget for re-embedding the whole corpus whenever the model changes, and version every vector with its model ID.
5.  **Index:** HNSW (in-memory, best recall/latency) or IVF-PQ / DiskANN (SSD-resident, cheaper) sharded by hash or by tenant. Add a BM25/SPLADE inverted index (OpenSearch/Elasticsearch/Vespa) next to it. Keep metadata filters in the same engine so that filtering happens *during* ANN traversal.
6.  **Incremental updates:** CDC stream, then re-parse, then upsert. Tombstone deletions immediately, because deletes are a compliance issue and not only a relevance one. Run periodic compaction and rebuilds, since HNSW degrades under heavy deletes.
#### Online path (latency budget for \~2.5s p95)
|  |  |
| :- | :- |
| **Stage** | **Budget** |
| Query rewrite / routing (small LLM or rules, optional) | 100-300 ms |
| Hybrid retrieval: ANN top-100 + BM25 top-100, fused with RRF, ACL-filtered | 30-80 ms |
| Cross-encoder rerank 200 → 20 (batched on GPU) | 80-200 ms |
| Context assembly (dedupe, parent expansion, ordering) | \<20 ms |
| Generation (\~8-15k token context, streaming) | TTFT 400-800 ms, total 1-2s |

  - **Query understanding:** decompose multi-hop questions, pull out filters such as dates and entities, and route out-of-scope or chit-chat queries away from retrieval.
  - **Generation:** instruct the model to answer only from the provided passages, cite chunk IDs, and abstain when evidence is missing. Put the strongest passages at the start and end because of the lost-in-the-middle effect. Use prompt caching for the static system prompt.
  - **Caching:** semantic cache for frequent queries (often 10-30% hit rate in enterprise settings), and an embedding cache for queries.
#### Cost back-of-envelope
At 50 QPS with \~12k input tokens per query, that is \~4.3M queries/day and \~50B input tokens/day. Generation dominates cost by more than 10× over retrieval. The levers that matter are fewer and better chunks (which is where the reranker pays for itself), smaller models for easy queries, and caching. Retrieval infra for \~100M vectors runs a few thousand dollars a month either way.
#### How to measure
  - **Retrieval:** recall@20 and nDCG@10 on a golden set of 500-2,000 queries labeled by SMEs and stratified by query type. Target **recall@50 ≥ 0.95 before the reranker, and recall@10 ≥ 0.85 after**. Track ANN recall against exact kNN separately (target ≥ 0.95) so that index tuning does not hide inside model changes.
  - **Generation:** faithfulness/groundedness (claims supported by the cited chunks), answer correctness, citation precision, and abstention accuracy on unanswerable queries. Use an LLM judge calibrated against \~200 human labels and report its agreement rate.
  - **Online:** thumbs and escalation rate, query reformulation rate, and click-through on citations. A/B test with guardrail metrics for latency and cost per query.
  - **Regression gate:** every change to the chunker, embedder, index params or prompt runs the offline suite in CI.
#### What a principal would add
  - Define **ownership boundaries**: ingestion, retrieval and generation have separate evals and on-call. That way a quality drop can be traced to a stage in minutes.
  - Plan for **embedding model migration** from day one: dual-write indices and shadow traffic.
  - Treat **"exhaustive" questions** ("list all contracts with clause X") as a different product: structured extraction into a table. Do not stretch top-k RAG to cover them.
### Tradeoffs
|  |  |  |  |
| :- | :- | :- | :- |
| **Option** | **Pros** | **Cons** | **When to choose** |
| HNSW in-memory | Best recall/latency (\<10 ms), mature | RAM-heavy (\~1.5-2× vector size), weak with deletes | Latency-critical work and a budget for RAM |
| IVF-PQ / DiskANN on SSD | 5-20× cheaper memory, scales to billions | Lower recall without rescoring, more tuning | Cost-sensitive, very large corpora |
| Managed vector DB (Pinecone, etc.) | Fast to ship, ops handled | Cost at 100M vectors, less control over hybrid | Small team, time to market |
| Search engine with vectors (Vespa/OpenSearch/Elastic) | Hybrid, filters and BM25 in one system | Heavier ops | Hybrid plus complex filters/ACLs |
| Long-context stuffing, no retrieval | Simple | Impossible at 25B tokens | Only for small per-user corpora |

  - **Pre-filter vs post-filter ACLs:** post-filtering top-k on a selective ACL can return zero results and leaks timing information. Prefer filtered ANN or per-tenant shards.
  - **Chunk size vs reranker cost:** smaller chunks give better precision but more candidates to rerank. Small-to-big expansion gets both.
  - **Fine-tuning the embedder:** usually +5-15 points of recall in-domain, but it locks you into a re-embedding cycle.
### Pitfalls interviewers probe
  - Jumping to "vector DB plus GPT" with no SLOs, no eval set and no capacity math (vectors × dims × bytes).
  - Ignoring ACLs and deletion. Retrieval-time permission leaks and stale deleted content are the incidents that actually get escalated.
  - Reporting end-to-end answer quality without separating retrieval recall from generation faithfulness.
  - Forgetting that ANN recall degrades with filters, deletes and index drift. You have to monitor it against exact kNN on a sample.
  - No plan for re-embedding 100M chunks when the embedding model changes.
  - Unbounded context, "just send top-50", which raises cost and latency and also hurts quality through distraction.
### Sources and further reading
  - [Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks (Lewis et al., 2020)](https://arxiv.org/abs/2005.11401): the original RAG formulation.
  - [Efficient and robust approximate nearest neighbor search using HNSW (Malkov & Yashunin)](https://arxiv.org/abs/1603.09320): the default ANN graph index.
  - [The Faiss library (Douze et al., 2024)](https://arxiv.org/abs/2401.08281): IVF, PQ and the memory/recall tradeoffs at scale.
  - [Introducing Contextual Retrieval (Anthropic)](https://www.anthropic.com/news/contextual-retrieval): chunk contextualization plus hybrid search plus reranking, with measured failure-rate reductions.
  - [Lost in the Middle: How Language Models Use Long Contexts (Liu et al., 2023)](https://arxiv.org/abs/2307.03172): why context ordering and size matter.

## Q2. Your RAG gives wrong answers. Debug it
### Short answer
"Wrong answers" is a symptom, so the first step is to localize it to a stage. I collect a set of failing cases and trace each one through the pipeline, then bucket the failures. The buckets: the answer isn't in the corpus; it's in the corpus but wasn't retrieved; it was retrieved but ranked out of the context; it was in the context but the model ignored or misread it; or the question was ambiguous or the label is wrong. The bucket counts tell me where to spend effort. Usually more than half land in retrieval and parsing, not in the LLM. Then I fix the dominant bucket, add those cases to a regression set, and gate future changes on it.
### Detailed answer
#### Clarifying questions
  - What does "wrong" mean: factually incorrect, incomplete, outdated, hallucinated citation, or a refusal? Who reported it, and what is the base rate? (Is it 3 anecdotes or 8% of traffic?)
  - Did something change recently, such as the embedding model, chunker, index rebuild, prompt, LLM version, or a corpus update? Sudden regressions are almost always a deploy or a data change.
  - Is it concentrated in a query type, tenant, language, document type or time range?
#### Step 1: Build the failure set
Pull 50-200 failing examples from logs: thumbs-down, escalations, and a random sample graded by an LLM judge. Make sure you log, for every request, the rewritten query, the retrieved IDs with scores at each stage, the final prompt, the model version, and the output. **If you can't replay a request exactly, fixing observability is step zero.**
#### Step 2: Attribute each failure to a stage (the core move)
For each case, have an SME (or a strong model, then human spot-checks) find the gold evidence chunk(s), then walk downstream:
|  |  |  |
| :- | :- | :- |
| **Check** | **Question** | **Typical fix** |
| Corpus coverage | Does the gold evidence exist in the raw source? | Content gap; ingestion missed the source |
| Parsing | Is it intact in the parsed text? (tables flattened, OCR garbage, headers dropped) | Better parser, table handling |
| Chunking | Is the evidence split across chunks, or separated from the context that disambiguates it? | Structure-aware chunks, overlap, context headers |
| Index | Is the chunk in the index, current, with the right ACL/metadata? | Fix the pipeline, stale index, filter bugs |
| Retrieval | Is gold in the top-200 candidates? In the top-k after fusion? | Hybrid search, query rewriting, embedder fine-tune |
| Ranking | Is gold in the final context window? | Reranker, k, dedupe |
| Generation | Gold is in context but the answer is wrong | Prompt, ordering, model choice, less noise |
| Eval/label | Is the "expected" answer actually wrong or ambiguous? | Fix the golden set |

Build a histogram. A typical real-world distribution I'd expect: \~10-20% corpus/parsing, \~30-40% retrieval/ranking, \~20-30% generation, \~10-20% ambiguous or bad labels. That last bucket is important: you can't fix what was never broken.
#### Step 3: Targeted diagnostics per bucket
  - **Retrieval misses:** compare against BM25 and against exact (brute-force) kNN. If exact kNN finds gold but ANN doesn't, it's index params (efSearch, nprobe) or filtered-ANN recall collapse. If neither finds it, it's a representation problem: vocabulary mismatch (acronyms, IDs, part numbers favor BM25), the query is phrased very differently from the doc (try HyDE or query rewriting), or the domain shifted away from the embedder's training data.
  - **Ranking misses:** gold is at rank 40 and k=10. Add or tune a cross-encoder reranker, and check that the reranker sees the chunk *with its title/section header*.
  - **Generation failures:** run an ablation. Give the model *only* the gold chunk. If it now answers correctly, the problem is distraction from irrelevant context, so reduce k, rerank harder, and order the best evidence first. If it still fails, the problem is reasoning or instruction: improve the prompt, require quote-then-answer, use a stronger model, or decompose multi-hop questions.
  - **Stale or conflicting docs:** the model picked an old version of a policy. Add date metadata, recency boosting, and dedupe near-duplicates. Instruct the model to prefer the newest source and to flag conflicts.
  - **Hallucinated citations:** validate that cited IDs were actually in the context, and verify each claim against its cited span with an NLI or judge model before returning.
#### Step 4: Fix, measure, prevent
  - Fix the largest bucket first, then re-run the whole golden set and not only the failures. Fixes like a smaller k or a new chunker routinely regress other slices.
  - Report per-stage metrics: retrieval recall@k, context precision, faithfulness, answer correctness, abstention rate. Use paired comparisons on the same queries, and bootstrap CIs. On 300 queries, a 2-point change is usually noise.
  - Add every root-caused failure to a **regression suite** with its stage label, and gate deploys on it.
  - Online: monitor retrieval score distributions, the empty-result rate, abstention rate, and the share of answers with zero valid citations. Drift in these usually shows up before user complaints.
#### What a principal would add
  - Build the **tooling** that lets anyone on the team do this triage in minutes: a trace viewer with stage-by-stage gold-hit indicators. Debugging RAG is a recurring workflow, not a one-time heroic effort.
  - Watch for **Goodhart on the LLM judge**. Calibrate the judge against humans (target ≥85% agreement) and re-check it after prompt changes.
  - Escalate the systemic issue. For example, if 15% of failures are content gaps, that's a product and data-ownership conversation, not a modeling problem.
### Tradeoffs
|  |  |  |  |
| :- | :- | :- | :- |
| **Option** | **Pros** | **Cons** | **When to choose** |
| Stage-wise error attribution (manual/SME) | Highest-signal root cause | Slow, \~2-5 min per case | First pass, and any new failure class |
| LLM-judge attribution at scale | Covers thousands of cases cheaply | Judge errors, needs calibration | After the taxonomy is stable |
| Swap to a bigger LLM | Quick, fixes some reasoning failures | Doesn't fix retrieval; adds cost and latency | Only when ablation shows gold-in-context failures |
| Tune retrieval (hybrid, rerank, fine-tune) | Fixes the most common bucket | Re-index cost, possible regressions | Recall@k on gold is low |
| Add verification/abstention layer | Cuts hallucination | \+latency, more refusals | High-stakes domains |

  - The key judgment is **don't touch the prompt or model until you know gold made it into the context**. Most teams invert this order.
  - Raising k trades precision and cost for recall. Measure it; don't assume it helps.
### Pitfalls interviewers probe
  - Starting with prompt tweaks or a model upgrade before measuring whether retrieval found the evidence.
  - Debugging from 3 anecdotes with no failure set, no traces and no base rate.
  - Only re-testing the failing cases, which causes regressions elsewhere. Always re-run the full stratified suite.
  - Ignoring the "label is wrong / question is ambiguous" bucket. It inflates the apparent error rate and misdirects work.
  - Missing filtered-ANN recall collapse, or a silent embedding-model/version mismatch between the query and document encoders.
  - Treating faithfulness and correctness as the same thing. A faithful answer to an outdated document is still wrong.

  - [RAGAS: Automated Evaluation of Retrieval Augmented Generation (Es et al., 2023)](https://arxiv.org/abs/2309.15217): faithfulness, context precision and recall metrics.
  - [ARES: An Automated Evaluation Framework for RAG Systems (Saad-Falcon et al., 2023)](https://arxiv.org/abs/2311.09476): LLM judges with statistical calibration against human labels.
  - [Large Language Models Can Be Easily Distracted by Irrelevant Context (Shi et al., 2023)](https://arxiv.org/abs/2302.00093): why more context can mean worse answers.
  - [Lost in the Middle (Liu et al., 2023)](https://arxiv.org/abs/2307.03172): position effects when gold is in context but ignored.
  - [Precise Zero-Shot Dense Retrieval without Relevance Labels / HyDE (Gao et al., 2022)](https://arxiv.org/abs/2212.10496): a query-side fix for phrasing mismatch.

## Q3. Pick a chunking strategy for legal contracts
### Short answer
Contracts are highly structured and full of cross-references, so I'd chunk along the document's own hierarchy (article, section, clause) rather than by fixed token windows. I'd keep each clause whole when it fits (\~200-1,000 tokens) and split long clauses at sub-clause boundaries. Each chunk carries its heading path, the contract's identity (parties, type, effective date) and resolved defined terms as context. Small clause-level chunks are used for retrieval, and the full section or parent is expanded at generation time. Then I'd validate the choice empirically on a clause-retrieval eval like CUAD or LegalBench-RAG, because chunking is a hyperparameter you measure rather than argue about.
### Detailed answer
#### Clarifying questions
  - **Task:** Q\&A over one contract, search across thousands ("which contracts have uncapped indemnity?"), clause comparison against a playbook, or extraction into fields? Cross-corpus "find all" tasks push toward structured extraction rather than pure chunk retrieval.
  - **Source quality:** native PDFs/DOCX vs scanned images, redlines, exhibits, schedules, amendments.
  - **Size:** contracts range from 5 to 300+ pages. Master agreements plus amendments mean the *governing* text may live in a later document.
  - **Precision requirement:** legal users need exact clause text and citations to section numbers. Paraphrase-level retrieval isn't enough.
#### Why naive chunking fails on contracts
  - **Fixed 512-token windows** split clauses mid-sentence and separate "Notwithstanding the foregoing..." from what it modifies. Exceptions and carve-outs often sit in a different chunk from the rule, which is exactly how you get confidently wrong answers.
  - **Defined terms:** "Confidential Information" is defined in §1.4 and used in §9. A §9 chunk alone doesn't say what it covers.
  - **Cross-references:** "subject to Section 12.3" and "except as set forth in Schedule B".
  - **Boilerplate similarity:** thousands of near-identical governing-law clauses across contracts. Without contract-level metadata, retrieval can't tell *whose* clause it found.
#### Recommended strategy
1.  **Parse to a structure tree.** Detect the numbering hierarchy (Article 5 → 5.2 → 5.2(a)(ii)) from layout and regexes, with an LLM fallback for messy docs. Keep tables (payment schedules, SLAs) intact as Markdown. Treat exhibits and schedules as separate subtrees.
2.  **Clause-level chunks.** One chunk per lowest heading that fits in \~800 tokens. Merge tiny siblings (e.g., one-line sub-clauses) up to \~200 tokens minimum, and split oversized clauses at sub-clause boundaries with a small overlap (\~1-2 sentences). Typical result: 50-300 chunks per contract.
3.  **Context header per chunk** (prepended for embedding and BM25, stored separately for display): \[Contract: MSA, Acme Corp ↔ Globex, effective 2023-04-01\] \[Section 9.2 Limitation of Liability \> (b) Exceptions\] Optionally add a 1-2 sentence LLM-generated summary situating the clause (contextual retrieval). Given contract-level boilerplate, this matters more for legal text than for most domains.
4.  **Defined-terms resolution:** extract the definitions section into a lookup. At retrieval time, attach the definitions of capitalized terms that appear in the retrieved chunk. Don't inline them into every chunk, because that bloats it and dilutes the embedding.
5.  **Cross-reference graph:** store edges for "Section X refers to Section Y". At generation time, pull in one hop of referenced clauses, at least for "subject to" and "notwithstanding" links.
6.  **Hierarchical/parent retrieval:** retrieve on clauses, then expand to the parent section for the LLM when the answer needs surrounding context. Also keep a contract-level summary chunk for routing ("which contracts are with Globex").
7.  **Metadata for filtering:** contract type, parties, dates, governing law, version/amendment lineage, and a superseded\_by link so retrieval prefers current terms.
#### Retrieval pairing
Legal queries mix semantics ("cap on liability") with exact strings ("Section 7.3", "LIBOR", party names), so use hybrid BM25 plus dense retrieval with a legal-domain or fine-tuned reranker. Answer generation should quote the clause verbatim with its section number.
#### How to measure
  - Build an eval of 200-500 queries with gold clause spans, starting from CUAD's 41 clause categories and LegalBench-RAG's span-level labels, plus in-house questions.
  - Metrics: **span-level recall@k** (did a retrieved chunk overlap the gold span?) and **precision** (how much irrelevant text was fed to the model). LegalBench-RAG evaluates precision and recall at the character-span level for exactly this reason. Also measure answer correctness with an attorney-labeled subset.
  - Compare chunkers head to head with the rest of the pipeline held fixed: fixed-512 with 10% overlap, recursive character splitting, structure-aware clause chunking, structure plus context headers, and late chunking. In my experience, structure-aware chunking with context beats fixed windows by a wide margin on clause recall, but the point of the exercise is to show the numbers on *your* contracts.
  - Slice by contract length, scan vs native, and query type (single-clause vs cross-reference vs cross-contract).
#### What a principal would add
  - For portfolio questions ("all contracts with auto-renewal under 30 days notice"), chunking is the wrong abstraction. Run **clause extraction into a structured table** at ingest and query it with SQL. RAG then handles only the long tail.
  - Amendments override the base agreement. Model **document lineage explicitly**, or the system will cite superseded terms. That is a liability risk, not just a quality bug.
### Tradeoffs
|  |  |  |  |
| :- | :- | :- | :- |
| **Option** | **Pros** | **Cons** | **When to choose** |
| Fixed-size windows (512 tok, overlap) | Trivial, robust to bad parsing | Splits clauses, loses carve-outs | Baseline only, or unparseable scans |
| Recursive/sentence splitting | Respects sentences | Ignores legal hierarchy | Mixed-quality corpora as a fallback |
| Structure-aware clause chunks | Aligns with how lawyers cite and query | Needs a good parser; variable sizes | Default for contracts |
| Clause chunks + contextual headers/summaries | Disambiguates boilerplate across contracts | Ingest-time LLM cost (\~$1/M tokens with caching) | Multi-contract corpora |
| Whole-contract in long context | No chunking errors | Expensive per query; mid-context recall drops | Single-contract Q\&A, \<100 pages |
| Structured extraction to table | Exact, exhaustive, auditable | Fixed schema, upfront labeling | Portfolio analytics, compliance |

  - Chunk size trades precision against completeness. Clause-level chunks plus parent expansion gets most of both.
  - Overlap is a weak patch for structure. Prefer explicit links (definitions, cross-references) over a bigger overlap.
### Pitfalls interviewers probe
  - Choosing chunk size by intuition ("512 feels right") instead of measuring span-level recall on a legal eval.
  - Separating exceptions and carve-outs from the rule they modify, which gives answers that are confidently wrong in the costliest direction.
  - Ignoring defined terms and cross-references.
  - No contract identity in the chunk, so a near-identical clause from the wrong contract gets retrieved.
  - Ignoring amendments and superseded versions.
  - Losing table structure (fee schedules, SLAs) during PDF parsing.

  - [LegalBench-RAG: A Benchmark for Retrieval-Augmented Generation in the Legal Domain (Pipitone & Alami, 2024)](https://arxiv.org/abs/2408.10343): span-level retrieval benchmark that compares chunking strategies.
  - [Introducing Contextual Retrieval (Anthropic)](https://www.anthropic.com/news/contextual-retrieval): prepending chunk-specific context before embedding and BM25 indexing.
  - [Late Chunking: Contextual Chunk Embeddings Using Long-Context Embedding Models (Günther et al., 2024)](https://arxiv.org/abs/2409.04669): embed the whole doc first, then pool per chunk, as an alternative to context headers.
  - [Lost in the Middle (Liu et al., 2023)](https://arxiv.org/abs/2307.03172): why stuffing whole contracts into context isn't free.
  - [Seven Failure Points When Engineering a RAG System (Barnett et al., 2024)](https://arxiv.org/abs/2401.05856): includes chunking and consolidation failures.
## Q4. BM25 vs dense vs hybrid search: when to use each
### Short answer
BM25 wins on exact tokens: identifiers, rare terms, names, error codes. It needs no training and is strong out of domain. Dense retrieval wins on paraphrase and semantic matching when queries and documents use different words, especially in-domain or after fine-tuning. Their errors are largely uncorrelated, so for almost any production system the default is **hybrid** (both retrievers, fused with RRF), followed by a reranker. The real answer is to run all three on a labeled set from your own traffic and choose by recall@k per query slice, because rankings flip across domains (BEIR showed BM25 beating many dense models zero-shot).
### Detailed answer
#### Clarifying questions
  - What do the queries look like? Keyword-ish (avg 2-3 tokens, IDs, SKUs) or natural-language questions?
  - How specialized is the domain vocabulary (biomed, legal, code, internal acronyms)? Is there in-domain training data, such as click logs or labeled pairs?
  - Multilingual? Latency and cost constraints? Is there an existing search stack (Elastic/OpenSearch/Vespa)?
#### How each works and where it breaks
  - **BM25 (sparse lexical):** term frequency with saturation (k1≈1.2) and length normalization (b≈0.75), times IDF. *Strengths:* exact match, rare-term precision, transparent, cheap (an inverted index; 100M docs is routine), zero training, robust to domain shift. *Weaknesses:* vocabulary mismatch ("car" vs "automobile"), no understanding of negation or intent, and weak on long natural-language questions.
  - **Dense (bi-encoder):** embed the query and the doc independently and use cosine/dot-product similarity over an ANN index. *Strengths:* synonyms, paraphrase, cross-lingual, conceptual queries. *Weaknesses:* weak on exact rare tokens (part numbers, names, codes get blurred), out-of-domain degradation, opaque failures, the cost of embedding and storing vectors, and re-indexing whenever the model changes. Off-the-shelf models can underperform BM25 on specialized corpora until fine-tuned.
  - **Learned sparse (SPLADE etc.):** a middle option. Model-predicted term weights plus expansion, served from an inverted index. It often matches dense quality in-domain with BM25-like interpretability and exact-match behavior.
  - **Late interaction (ColBERT):** token-level matching. Strong quality and good out-of-domain behavior, but 10-100× more storage than single-vector (mitigated by ColBERTv2 compression/PLAID).
#### Hybrid done right
1.  Run BM25 top-100 and dense top-100 in parallel (combined latency ≈ max(each), typically 10-50 ms).
2.  Fuse them. **Reciprocal Rank Fusion:** score(d) = Σ 1/(k + rank\_i(d)), with k≈60. It is scale-free and needs no score normalization, which makes it the right default. Weighted linear combination of normalized scores can beat RRF if you tune the weight α on labeled data, but it's brittle when score distributions drift.
3.  Rerank the fused top \~100-200 with a cross-encoder.
4.  Optionally use **query-dependent routing or weighting**: queries that look like IDs (regex for codes, quoted strings) get more BM25 weight; long questions get more dense weight.
Anthropic's contextual retrieval experiments show the additive pattern: contextual embeddings alone reduced top-20 retrieval failures by \~35%, adding contextual BM25 brought it to \~49%, and adding reranking to \~67%.
#### Decision guide
  - **BM25 only:** cold start with no labeled data, heavily keyword or identifier queries (log search, code symbols, legal citations, e-commerce SKUs), strict cost or latency limits, or when explainability is required. Also the right **baseline**: if your dense system doesn't beat BM25 on your eval set, stop and investigate.
  - **Dense only:** short-text semantic matching (FAQ dedup, support-ticket routing), cross-lingual retrieval, conversational queries with low lexical overlap, and corpora with little rare vocabulary. Even here I'd prove the BM25 component adds nothing before dropping it.
  - **Hybrid:** the default for general enterprise RAG, mixed query populations, and anywhere recall matters more than a few ms of latency. The added cost is running an inverted index next to the vector index, which is often free if you already run Elastic, OpenSearch or Vespa.
#### How to measure
  - A labeled set of 500-2,000 queries sampled from real traffic, stratified by type (navigational/ID, keyword, natural-language, multi-hop). Use pooled judgments: label the union of the top-20 from every system so you don't bias toward the incumbent.
  - Metrics: **recall@100 / recall@50** for the first stage (the reranker can only reorder what it gets) and **nDCG@10 / MRR** for the final list. Report **per slice**. The hybrid gain usually concentrates in the slice where one retriever collapses.
  - Measure **overlap**: if BM25 and dense top-50 sets overlap 80%+, hybrid adds little. At 30-50% overlap, fusion typically adds several points of recall.
  - Significance: paired bootstrap or a permutation test over queries. Report CIs.
  - Online: CTR on citations, answer acceptance, reformulation rate.
#### What a principal would add
  - The choice is not permanent. Instrument per-slice metrics so that traffic drift (more ID lookups after a product launch) shows up as a measurable retriever mismatch.
  - The biggest lever is often **in-domain fine-tuning of the dense model** using hard negatives mined from BM25. That uses each method to improve the other.
  - Consider the **operational surface**: two indices means two freshness pipelines and two failure modes. Make sure deletes and ACLs stay consistent across them.
### Tradeoffs
|  |  |  |  |
| :- | :- | :- | :- |
| **Option** | **Pros** | **Cons** | **When to choose** |
| BM25 | Exact match, no training, cheap, interpretable, robust OOD | Vocabulary mismatch, weak on NL questions | Keyword/ID queries, cold start, baseline |
| Dense bi-encoder | Semantic and paraphrase, multilingual | Misses rare tokens, domain shift, re-embed cost | Conversational queries, cross-lingual, fine-tuned domain |
| Learned sparse (SPLADE) | Semantic expansion on an inverted index, exact match retained | Larger index than BM25, inference cost at ingest | Want dense-like quality with lexical infra |
| ColBERT late interaction | Top quality, good OOD | Storage and serving complexity | Quality-critical, moderate corpus size |
| Hybrid (RRF) + reranker | Best recall across slices, robust | Two indices, more ops | Default for production RAG |

  - RRF vs a tuned linear blend: RRF is robust with zero tuning. A linear blend can win by 1-3 points but needs labels and re-tuning when models change.
  - Don't evaluate a first-stage retriever on nDCG@10 alone. Its job is recall at the reranker's depth.
### Pitfalls interviewers probe
  - Claiming "dense is strictly better than BM25". BEIR showed BM25 is a hard zero-shot baseline and many dense models lose out of domain.
  - Combining raw BM25 scores with cosine similarities without normalization (the scales are incompatible). Use RRF or calibrated normalization.
  - Evaluating on a public benchmark instead of your own query distribution and slices.
  - Pooling bias: labeling only the incumbent's results so the new retriever's finds count as "non-relevant".
  - Ignoring tokenization and analyzers for BM25 (stemming, code identifiers, CJK languages), which can matter as much as the algorithm choice.
  - Forgetting that hybrid needs consistent ACL filters and deletes across both indices.

## Q5. Add a reranker and measure if it helped
### Short answer
I'd add a cross-encoder reranker that rescores the first-stage top \~50-200 candidates and passes the top \~5-20 to the LLM. Then I'd judge it with a controlled comparison, not a vibe check. Offline: on a labeled, stratified query set, the reranker should raise nDCG@10 and recall@k at the *context cutoff k* with statistical significance. End to end, answer correctness and faithfulness should go up at equal or lower context size. Online: an A/B test on user-facing quality, with p95 latency and cost per query as guardrails. It "helped" only if the quality gain survives the latency budget and holds on every important slice.
### Detailed answer
#### Clarifying questions
  - What's the current pipeline, and what is first-stage **recall@N** at the candidate depth? A reranker can only reorder what it's given. If recall@100 is 0.70, the ceiling is 0.70 and the fix belongs upstream.
  - What latency budget is left? (A typical slot is 50-250 ms p95.)
  - Hosted API (Cohere Rerank, Voyage, etc.) or self-hosted (bge-reranker, monoT5, a fine-tuned cross-encoder)? Data-residency constraints?
  - What does the LLM consume: top-5 or top-20? That k is the metric cutoff that matters.
#### Design
1.  **Candidate depth N:** start at 100. Plot recall@N for the first stage. Pick N where the curve flattens (often 50-200), because deeper N costs linear latency.
2.  **Model choice:**
      - *Cross-encoder* (BERT/MiniLM/XLM-R-class, \~20-600M params) scores each (query, passage) pair jointly with full attention. A \~100M-param model on one GPU reranks 100 passages of \~256 tokens in roughly 30-100 ms when batched.
      - *LLM listwise/pointwise rerankers* (RankGPT-style) are strong zero-shot but cost 10-100× more. Use them for distilling a smaller model, or for low-QPS, high-value queries.
      - *Late interaction (ColBERT)* is a cheaper middle ground and can serve as the reranker.
3.  **Input formatting:** feed title plus section header plus chunk text, truncated to the model's max length (often 512 tokens). Headers matter a lot, and truncation silently drops evidence from long chunks.
4.  **Output policy:** take the top-k by score, and optionally drop candidates below a calibrated threshold so the LLM gets fewer, better passages. That often cuts tokens and cost by 30-50%, which can pay for the reranker.
5.  **Fine-tuning (phase 2):** use in-domain pairs from clicks/citations or LLM-labeled data, with hard negatives from the first stage. Domain fine-tuning commonly adds several nDCG points over off-the-shelf.
#### Offline measurement
  - **Eval set:** 500-2,000 real queries, stratified, with graded relevance judgments pooled from the top-20 of *both* the baseline ranking and the reranked list. Otherwise newly surfaced relevant passages count as misses.
  - **Retrieval metrics at the cutoff the LLM sees:** nDCG@10, recall@5/@10, MRR. Also report recall@N of the first stage, to show the ceiling.
  - **Statistics:** paired comparison per query (same queries, two systems), with a paired bootstrap or permutation test and 95% CIs. On \~1,000 queries, a +2-3 point nDCG@10 gain is typically detectable. Report the win/tie/loss distribution per query, not only the mean. A reranker that helps 30% of queries and hurts 10% needs a look at the losers.
  - **End to end:** run the full RAG pipeline with and without the reranker, holding the LLM, prompt and k fixed. Measure answer correctness, faithfulness and citation precision with an LLM judge calibrated on human labels. Also run a variant **with the reranker and a smaller k** (e.g., 5 vs 10), since a common win is the same quality at half the tokens.
  - **Slices:** query type, length, language, doc type, and whether gold was already at rank 1 (no headroom there). Watch especially for regressions on exact-match/ID queries, where cross-encoders sometimes demote lexically exact hits.
  - **Ablations:** confirm the gain isn't just from reranking deeper (did N change too?) or from the formatting change.
#### Online measurement
  - An A/B test with a pre-registered primary metric (e.g., answer acceptance rate, or the rate of conversations resolved without escalation) and guardrails: p95/p99 latency, timeout rate, cost per query, abstention rate.
  - Power analysis up front. Small quality changes in noisy implicit-feedback metrics need large samples, so pre-compute the minimum detectable effect.
  - Optionally use **interleaving** for ranking-quality comparison, which is far more sensitive per query than A/B on click metrics.
  - Monitor reranker score distributions for drift. Add a timeout fallback to the first-stage order if the reranker exceeds its budget, so tail latency is protected.
#### Cost/latency accounting
Self-hosted: one GPU at roughly $1-2/hr serving \~20-50 QPS for 100-candidate reranks gives a cost per 1,000 queries in the cents. That is small next to generation if the reranker lets you drop k from 20 to 8 chunks (\~6k fewer input tokens per query). Present it as **net** cost: reranker cost minus tokens saved.
#### What a principal would add
  - Decide in advance what "helped" means. I'd write the decision rule before running the experiment: ship if end-to-end correctness gains ≥2 points with a CI excluding 0, no slice regresses by more than 1 point, and p95 rises by no more than 150 ms. That prevents post-hoc rationalization.
  - Treat the reranker as the **cheapest place to inject domain knowledge**. It is fine-tunable without re-indexing, unlike the embedder.
### Tradeoffs
|  |  |  |  |
| :- | :- | :- | :- |
| **Option** | **Pros** | **Cons** | **When to choose** |
| No reranker, tune first stage | Lowest latency, simplest | Lower precision at small k | Very tight latency or first-stage nDCG already high |
| Small cross-encoder (\~20-100M) | 20-60 ms, big precision gain | 512-token limit, generic domain | Default production choice |
| Large cross-encoder / hosted API | Higher quality, multilingual | 100-300 ms, per-call cost, data egress | Quality-critical, moderate QPS |
| LLM listwise reranking | Best zero-shot, handles reasoning | 10-100× cost, seconds of latency | Offline labeling/distillation, low-QPS high-value |
| ColBERT as reranker | Cheap, strong | Index storage, infra | Already running late interaction |

  - Depth N vs latency: reranking cost is linear in N, and gains usually flatten past 100-200.
  - Gains in offline nDCG don't always translate end to end. A strong LLM may already handle a slightly noisy top-10, so measure both.
### Pitfalls interviewers probe
  - Measuring only the mean nDCG gain with no paired significance test, slices or per-query win/loss analysis.
  - Ignoring first-stage recall@N. A reranker cannot recover documents it never sees.
  - Pooling bias: judgments only on the baseline's results understate the reranker's gains, or overstate them if pooled the other way.
  - Silent truncation: long chunks cut at 512 tokens drop the relevant span, and the reranker scores the wrong text.
  - Forgetting the latency tail and failure mode. Have a timeout fallback, and know the p99 behavior under load.
  - Declaring victory on retrieval metrics without an end-to-end answer-quality check, or without counting the token savings that might make it net cheaper.
